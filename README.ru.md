# ProofGram — Протокол шифрования

В этой папке находится полный открытый исходный код криптографического ядра **ProofGram** — бота для сквозного шифрования архива Telegram Business сообщений.

> **Сервер никогда не видит содержимое сообщений.** Всё шифрование и дешифрование происходит на устройстве пользователя. Приватный ключ никогда не покидает устройство.

---

## Общая архитектура

```
┌─────────────────────────────────────────────────────────┐
│               Telegram Business Бот (сервер)             │
│   Получает сообщение → шифрует публичным ключом          │
│   → сохраняет шифротекст в БД / S3                      │
└──────────────────────────┬──────────────────────────────┘
                           │ зашифрованный blob (сервер не читает)
                           ▼
┌─────────────────────────────────────────────────────────┐
│                  Мини-апп (браузер)                      │
│   Загружает приватный ключ из IndexedDB                  │
│   → дешифрует локально → показывает сообщение           │
└─────────────────────────────────────────────────────────┘
```

---

## Генерация ключей (`client/keys.ts`)

```
BIP39 мнемоника (12 слов, 128 бит энтропии)
    │
    ▼ bip39.mnemonicToSeed() — PBKDF2, 2048 итерации
64-байтовый seed
    │
    ▼ HKDF-SHA256(seed, salt="messagesgram-x25519", info="key-derivation", 32 байта)
32-байтовый X25519 приватный ключ  ← хранится в IndexedDB (никогда не отправляется)
    │
    ▼ x25519.getPublicKey()
32-байтовый X25519 публичный ключ  ← кодируется base64, отправляется на сервер при регистрации
```

- Тип ключа: **X25519** (Curve25519 Диффи-Хеллман)
- Источник энтропии: `bip39.generateMnemonic(128)` — 12 слов
- Хранение приватного ключа: **IndexedDB** (только браузер), никогда не передаётся
- Формат публичного ключа: 32 байта, base64 (44 символа)

## Шифрование сообщений — ECIES (`server/encrypt.ts`)

Выполняется ботом на сервере при получении нового Business сообщения.

```
Входные данные: текст сообщения, X25519 публичный ключ пользователя

1. Генерация одноразовой (эфемерной) пары X25519 ключей — уникальная для каждого сообщения

2. ECDH:
   shared_secret = DH(ephemeral_private, user_public)   ← 32 байта

3. HKDF-SHA256:
   aes_key = HKDF(shared_secret, salt=ephemeral_public, info="messagesgram-v1", 32 байта)

4. Шифрование AES-256-GCM:
   iv = случайные 12 байт
   ciphertext || auth_tag = AES-GCM(aes_key, iv, plaintext)

5. Сохранение в базу данных:
   encrypted_content  = base64(ciphertext || auth_tag)   ← auth_tag 16 байт в конце
   encrypted_aes_key  = base64(ephemeral_public_key)     ← поле переиспользовано для совместимости
   iv                 = base64(iv)
```

**Сервер немедленно уничтожает эфемерный приватный ключ после шифрования.**  
В базе остаётся только эфемерный *публичный* ключ — без приватного ключа пользователя он бесполезен.

## Дешифрование сообщений — ECIES (`client/keys.ts`)

Выполняется полностью в браузере (мини-апп).

```
Входные данные: encrypted_content, encrypted_aes_key (= эфемерный публ. ключ), iv, приватный ключ (hex)

1. ECDH:
   shared_secret = x25519.getSharedSecret(user_private, ephemeral_public)

2. HKDF-SHA256:
   aes_key = HKDF(shared_secret, salt=ephemeral_public, info="messagesgram-v1", 32 байта)

3. Дешифрование AES-256-GCM:
   combined   = base64_decode(encrypted_content)
   ciphertext = combined[0 .. len-16]
   auth_tag   = combined[len-16 .. len]
   plaintext  = AES-GCM-Decrypt(aes_key, iv, ciphertext, auth_tag)
```

Если проверка `auth_tag` не проходит → дешифрование выбрасывает ошибку, содержимое не показывается.

## Резервная копия ключа (`client/keys.ts`)

Приватный ключ можно экспортировать в зашифрованный файл для восстановления.

```
Входные данные: приватный ключ (hex), пароль пользователя

v2 (текущий):
  salt = случайные 32 байта
  key  = PBKDF2-SHA1(пароль, salt, 600_000 итераций, 32 байта)
  iv   = случайные 12 байт
  encrypted_key || tag = AES-256-GCM(key, iv, private_key_hex)

Выходной JSON: { version: 2, salt, iv, tag, data }
```

- 600 000 итераций PBKDF2 — устойчиво к перебору
- AES-GCM обеспечивает аутентифицированное шифрование — обнаруживает подмену бэкапа
- Бэкапы v1 (AES-CBC, 100к итераций) поддерживаются только для чтения (миграция)

## Аутентификация API (`auth/initdata-validation.ts`)

Мини-апп аутентифицируется на бэкенде через механизм Telegram `initData`.

```
Telegram подписывает initData через: HMAC-SHA256(data_check_string, secret_key)
  где secret_key = HMAC-SHA256("WebAppData", bot_token)

Сервер проверяет:
  1. Пересчитывает HMAC — сравнение за константное время (crypto.timingSafeEqual)
  2. Проверяет TTL поля auth_date: максимум 1 час
  3. Выдаёт серверный токен сессии (32 случайных байта, TTL 1 час)
     → возвращается в заголовке ответа X-Session-Token
  4. Следующие запросы используют X-Session-Token (без повторного вычисления HMAC)
```

## Ротация ключей / Подпись

При смене ключевой пары пользователь должен доказать владение старым ключом.

```
Ротация EC ключа:
  1. Клиент подписывает новый публичный ключ старым Ed25519 ключом
     (байты X25519 приватного ключа переиспользуются как Ed25519 приватный ключ)
  2. Бэкенд проверяет подпись Ed25519
  3. Только при успешной проверке → публичный ключ обновляется в БД

Ротация RSA ключа (legacy):
  Используется подпись RSA-SHA256
```

## Свойства безопасности

| Свойство | Значение |
|---|---|
| Схема шифрования | ECIES (X25519 + HKDF-SHA256 + AES-256-GCM) |
| Согласование ключей | X25519 (Curve25519) |
| KDF | HKDF-SHA256 |
| Симметричный шифр | AES-256-GCM (аутентифицированный) |
| Получение ключа из мнемоники | BIP39 PBKDF2 → HKDF-SHA256 |
| Шифрование бэкапа | AES-256-GCM + PBKDF2 (600к итер.) |
| Аутентификация | HMAC-SHA256 (Telegram initData) + токен сессии |
| Хранение ключа | IndexedDB (только браузер, не передаётся) |
| Прямая секретность | Эфемерные ключи на каждое сообщение |
| Знания сервера | Ноль — видит только шифротекст и эфемерные публичные ключи |
